Summary

Nova is a voice assistant that runs entirely on the phone, with no server and no internet. Speech goes to whisper base.en, then to a FunctionGemma 270M model fine-tuned with LoRA on 20k examples and quantised to INT8. The model only proposes tool calls. ToolGate validates them, asks for confirmation and checks permissions before one of 43 tools runs. It reaches 94.9% exact tool calls at about 0.9 s per request on a mid-range phone, and it also turns screenshots into calendar events, checks messages for scams, and detects falls with an SOS alert.

The main idea: a small model is enough for this job when deterministic code checks its output and handles the easy cases without it.

1. A request, stage by stage

  1. Wake word. sherpa-onnx keyword spotter (zipformer transducer, int8, 5.25 MB), keywords “HEY NOVA” and “HE NOVA” so Indian-English voices are heard. It runs inside a foreground service while the phone is unlocked with the screen on, never while Nova is speaking, and hands the live microphone to the recorder with 0.5 s of pre-roll so the first word isn't lost. A tap-to-talk button and typing work without it.
  2. End of speech. Silero VAD decides when the user has stopped (~0.85 s).
  3. Speech to text. whisper.cpp with base.en (q5_1, 60 MB): median 1.72 s per command on the phone. The decoder's runner-up words are kept as alternatives, and CommandText / SpokenForms pick the reading that makes sense as a command (“check my male” → mail).
  4. Deterministic routing, before any model. In order: the user's own taught phrases; SosRule (“Help!”, “I've fallen”); the FastPath for fixed-form commands (alarms, timers, flashlight, settings, opening apps, calculator, reminders, named timers, note search, household ledger); ChainRules for two-step requests in trained shapes; ContextRules for follow-ups (“what about tomorrow?”, “aur kal ka?”), “undo that” and “that's wrong”. Rules answer 44% of requests in ~0.1 s, with 100% precision on the test rows they claim. When a rule understands a request but can't do it as said (a reminder with no clear time), Nova says what is missing instead of guessing.
  5. Intent gate. A BERT-small classifier (fp16 ONNX, 57.6 MB) reads requests that are left. If no tool fits (P(none) ≥ 0.97), Nova says “say it another way”, so the model is never forced to pick a wrong tool.
  6. The model. FunctionGemma 270M, fine-tuned with LoRA on the Nova-20k dataset, merged and exported as an INT8 .litertlm (290 MB) for LiteRT-LM. Its prompt holds the 31 model-visible tool descriptions (~2.3k tokens) and must match the training prompt exactly. Prefill of that prompt is the main cost, cut with a 3072-token KV cache, 2 threads and read-ahead: ~0.9 s per request.
  7. Checks on what the model proposed. CutCall repairs the call markup so it is never read out; CallCheck runs a call only if the request names that tool's job; NameResolver matches contacts, places and apps by sound against the phone's own data (“Rear Row” → “Riya Rao”, or “isn't in your contacts”); ArgumentFixer / DateNormalizer correct dates and drop values that are not in the user's words (no invented phone numbers or email bodies).
  8. ToolGate, the only way to act. ToolValidator checks every argument against the schema in tools.json and rejects unknown tools; RepeatGuard stops loops; ConfirmationPolicy asks a fixed template (“Call Riya Rao?”), never model text, and reads the answer from closed yes/no word lists; PermissionChecker asks Android for what the tool needs. Only then does the executor run the tool.
  9. Tools and the agent loop. 43 tools: 31 the model can call, 12 reachable only by rules (emergency alert, household ledger, photo search…). Results go back to the model for the next step, at most 5 steps and 6 calls per request, each tool with a 5 s timeout. A failed or declined call returns an error to the model; nothing is guessed and executed. Messages and emails open as prefilled drafts. The reply is spoken by Android TTS (~0.19 s).

2. Screenshot → calendar

  1. Input. Share a screenshot to Nova, pick one, or turn on the N button: a JobScheduler content trigger on the photo library wakes Nova when a new screenshot is saved (no service running), and a small bubble offers it for 6 s. The capture time comes from the image's metadata or file name.
  2. OCR. ML Kit's Latin text recogniser, bundled in the app, reads the image as is and enlarged 1.5× (~0.8 s together).
  3. Layout. CardSegmenter and RealLayouts rebuild the notification cards, calendar detail pages and Zoom lists from the text boxes; OcrRepair fixes characters only inside time and date tokens (“1O:3O”) and flags the event when it does.
  4. MeetingParser. A card becomes an event only with a grounded start time and evidence it is a meeting (a meeting app or meeting words). Dates are taken in a fixed priority (explicit date, checked weekday, Today/Tomorrow, the capture day marked as assumed), “in 10 minutes” is counted from when the notice arrived, time zones are converted, meetings already over are skipped, and the same meeting notified by several apps is merged.
  5. Guards against misreads. A title word one edit away from a dictionary word is flagged (“Ofice hours”), and an event the 1.5× reading does not reproduce is flagged. A flagged event is shown as “check this”, never saved silently.
  6. Review. Every event is shown with the part of the screenshot it came from. Nothing is added until the user taps Add to calendar, which goes through ToolGate's confirmation like any other tool.

The same reader also finds receipts, bills and school notices, phone numbers and addresses. The scam check scores message text, links and UPI QR codes (it says whom a QR code pays) on the phone.

3. Fall detection and SOS

  1. Sensing. The accelerometer at ~50 Hz inside Nova's foreground service; with the screen off the wake-up accelerometer is batched so the phone can sleep.
  2. FallDetector (physics, no model): a drop below 0.6 g, then a hit above 2.2 g, then the phone lying still, turned at least 65° from before.
  3. FallGuard ignores a “fall” when the phone was just switched on or unlocked (taken out of a pocket) or a call is active.
  4. Alert. Over the lock screen: a buzz, “Are you OK?” out loud, big I'M OK / GET HELP buttons, and whisper listening for “I'm OK” or “help”. A siren starts at 30 s.
  5. SosSender. With no answer in 45 s, or on “help”, it texts the location to up to 3 emergency contacts and calls the first on speaker. This is the one action Nova takes without a yes. Test mode runs the whole alert and sends nothing. Saying “Help!” to Nova starts the same alert after 10 s.

Questions and answers

The model

Why a 270M model and not a bigger one?

It has to fit and run on a mid-range phone with no server. At INT8 it answers in ~0.9 s. The accuracy gap is closed by deterministic rules (FastPath, ArgumentFixer), which take it from 80.5% to 94.9% exact.

Why FunctionGemma?

It is built for function calling and small enough for a phone. Fine-tuning teaches it this app's 31 tools and their argument formats.

How was it fine-tuned?

LoRA on the Nova-20k dataset (20k request → tool-call examples), then merged into the base weights and exported as an INT8 .litertlm file for LiteRT-LM. The prompt at runtime must match the training prompt exactly, or accuracy collapses.

What does quantisation cost?

INT8 makes the model small and fast enough for the phone's CPU. The accuracy numbers above are measured on the INT8 model as deployed, not the fp32 one.

What was the latency bottleneck?

Prefill: reading the ~2.3k-token prompt with all the tool descriptions. It was cut with a KV cache of 3072, 2 threads and read-ahead. The GPU was measured and rejected. Shorter descriptions need a retrain.

Safety

What stops the model doing something dangerous?

It only proposes. ToolGate validates every argument against the catalogue, rejects unknown tools, and asks “yes/no” for calls, messages and payments. The answer is parsed from a closed word list, never by the model. Android permissions are checked, and the agent loop has step and call limits. No benchmark ever ran a confirm-only tool without a yes.

What if the model invents a phone number or an email body?

CallCheck only runs a model call if the request names that tool's job. ArgumentFixer drops values that aren't in the user's words. Contacts come from the address book by name, never from the model.

Does anything leave the phone?

Only web tools (weather, search, maps) use the internet. ML Kit's usage-log upload was removed from the manifest, and there is a local-only switch with a log of every network request.

Voice

Why whisper and not Moonshine?

Both were measured on the project's commands. whisper was more accurate, and base.en beat tiny.en (14.0% vs 20.2% word error rate).

How does the wake word work?

sherpa-onnx keyword spotting, with “HEY NOVA” and “HE NOVA” spellings for Indian-English voices. It listens while the phone is unlocked with the screen on: 144/150 recorded clips, 27/30 live Indian-English voices, and 0 false wakes in 1.87 hours of ordinary speech.

Does it understand Hinglish?

Partly. Follow-ups like “aur kal ka?” are handled by rules. Speech recognition is English (base.en).

Fall detection

How does it work without AI?

Physics: a drop below 0.6 g, a hard hit above 2.2 g, then lying still at an angle at least 65° from before. Thresholds were chosen on 13 people from the UMAFall dataset and tested once on 6 others: 54/56 falls, 4/149 false alarms. Jogging hits 4–5 g many times but never lies still afterwards.

Why not call 112 automatically?

A false alarm would reach emergency services. Nova asks “Are you OK?” (by voice and with buttons). If there's no answer in 45 s, it texts and calls a family contact.

Where do false alarms come from?

On the dataset, mostly from pulling the phone out to make a call, so a “fall” is ignored when the screen was just switched on or a call is active.

Evaluation

How do you know the numbers aren't overfitted?

Dev sets for tuning, held-out sets run once per milestone. The 185-command held-out set uses new people's wording. The 1,520-row test split shares templates with training, so the held-out gold sets are the numbers to trust.

How was it tested end to end?

The same Kotlin sources run on the laptop (JVM) with the real model, so the laptop runs and the phone runs agree, and every held-out number can be re-run in about 20 seconds. Voice was tested with synthetic voices plus live checks on the phone. There are 413 unit tests per build variant.

How it was built

How was the AI coding assistant used?

Claude Code wrote and ran most of the code, with me deciding the direction. Whisper base.en, the BERT tool gate, the Moonshine comparison and fall detection were my calls. Three files kept it honest: a frozen PLAN.md, a SPEC.md roadmap, and an Insights.md log of every finding and decision. Every change updated them and was committed. The whole development transcript is published with the project.

What did you learn?

Measure before deciding: GPU, Moonshine and prompt length were all decided by measurements, not assumptions. And around a small model, deterministic code is where reliability comes from.

Future work

  • Own-voice recordings to fine-tune whisper and widen the voice tests beyond synthetic voices.
  • A first-run model download (~390 MB) for a store release; the models are copied to the phone today.
  • Retrain with short tool descriptions to cut the prompt and latency.
  • Measure fall detection's battery cost and false alarms over days of real use, and test with older users' falls.
